> **Status**: 实施中 —— 阶段 1、2、3 已落地（2026-09-10），阶段 4 待做

> **Target Branch**: main

## 1. 美学定调与核心灵魂

### 1.1 明确否决卡片化（NO Card Enclosure）
- **终端的本质是行与字符，不是网页卡片**：在终端里强行套上边框盒子，会白白吞掉 4-6 行宝贵的垂直行高，在 24 行终端下将导致列表可见条目骤减 30%，产生强烈的视觉噪点与笨重感；
- **纯粹单栏平铺**：保持终端最自然、透气、高密度的极简排版。

### 1.2 为什么彻底放弃双栏中轴分割竖线（NO Vertical Divider `│`）
- **bash 下无法保证中轴竖线无缝且对齐**：列表标题包含中日韩、全角符号、Emoji 等混合字符，不同终端渲染存在亚像素/单字符宽度微小差异。在 bash 中逐行打印中轴竖线必然产生锯齿和对齐断裂；
- **裁决**：**坚决不做双栏中轴分割线，回归纯粹单栏**。

### 1.3 核心灵魂：全宽端到端（End-to-End）进度分割线
- **端到端纯净贯穿**：横跨整个终端宽度的水平线，**两端绝不放置数字时间戳**，整行纯净延伸，从左边缘一直贯穿到右边缘；
- **双重职能合并**：
  1. **天然物理分割线**：视觉上作为上方 Now Playing 状态区与下方歌曲列表区之间的自然水平分界线；
  2. **动态进度条与章节刻度**：在同一条轨道上，直观呈现已播段（重线/半块）、当前游标点、未播段（细线）以及章节标记断点（Chapter Breakpoints）；
- **时间指示器上浮**：将播放时间与总时长提取至上方正在播放标题行，以 **`【01:24/03:03】`** 格式紧凑呈现，与曲名和状态形成紧密整体。

## 2. 系统设计与视觉蓝图 (Visual Blueprint)

### 纯粹极简单栏标准视图（80~90 列）

```text

   ━━━━━━━━━━━━━━━━━━━━━●────────────────────────────────────────────────────────────────────

      1.  米津玄师 - Lemon                                                               04:15
   ▎  2.  【tsukimi】YELLOW / 神山羊                                                     03:03  █
      3.  YOASOBI - 夜に駆ける                                                           04:21  │
      4.  RADWIMPS - 前前前世                                                            04:45  │
      5.  宇多田光 - One Last Kiss                                                       04:12  │
      6.  周杰伦 - 七里香                                                                04:59  │

   ──────────────────────────────────────────────────────────────────────────────────────────
   [Enter] 播放   [Space] 暂停   [b] 歌单   [h] 历史   [c] 分P   [/] 过滤   [t] 主题   [q] 退出
```

- **层次极其分明**：
  - 上方为状态与当前播放曲目，曲名后紧随 **`【已播/总长】`** 紧凑徽章；
  - **中间唯一横向分割线**是全宽端到端、无数字打断的纯净动态进度条；
  - 下方为主列表区，选中行由左侧 Accent Bar（`▎`）优雅标记；
  - 底部由紧凑键帽排版整理快捷键。
- **全屏无框、通透呼吸、零排版漂移风险**。

## 3. 详细实施规格 (Implementation Spec)

实施分为 4 个清晰步骤：

### 阶段 1：时间戳上浮与端到端进度分割线 —— **已完成（2026-09-10）**

落地与本节原稿有三处出入，都是 grounding 推翻了前提之后按实测改的：

**1. 位置读数改为括号徽章（`shell/uting` Now-Playing 横幅）** —— 已做。
`GL_TIME_L`/`GL_TIME_R`（`【` `】`，`YT_ASCII=1` 回退 `[` `]`）随其余 chrome 字形声明。
它们是 East-Asian **Wide**，不是 Ambiguous，所以**不进任何 `CW_*` 表**：`char_w` 的兜底 2
对它们已经是精确值。原稿里 `PT_CUR` 为空时打 `【00:00/总长】` 那一条**没有采纳** ——
源码既有契约是"还没有读数就单独回退成时长"，打 `00:00` 是凭空发明一个读数；
括号形沿用了那条回退。直播形态取 `【已播 GL_LIVE】`，不硬写 `LIVE`：`PT_TOTAL` 在直播下
本来就由 `fetch_play_times` 播种成 `GL_LIVE`，硬写会绕开它的 ASCII 回退。

**2. 进度条全宽 —— 取 `nav_cols - 1`，不是 `right_edge`。** 原稿正文写 `bar_w=$right_edge`，
但 `right_edge = nav_cols - CW_AMBIG_W - 1`，那只是**左边多吃 2 格**、右端仍旧停在时长轨那一列，
与本文档蓝图那张图（横线压过滚动条、两侧都比列表宽）对不上。按蓝图取全宽。
**没取 `nav_cols`**：写终端最后一列会把光标留在延迟折行态，某些终端会把它兑现成一个真换行，
凭空多出一行 reflow 没计过的高度。右边留一格空气。

**3. `●` 游标点 —— 不做，维持现状。** `shell/uting` 的 `render_prog_bar` 上方那段注释
记录了这个字形**已经被试过并被否决**：`━`→`─` 的粗细变化本身就是播放头，
而"这一行上唯一的白就是章节边界"正是断口能被读成断口的原因；再放一个实心圆上去，
它会和章节断点争同一条视线。已在 88 宽下并排渲染两版给出判断，维持无播放头。
`render_prog_bar` **一个字没改**。

已验证：`bash -n shell/*`、`tests/contract.sh --offline`（273 ok / 0 failed）、
`tests/drive.sh -x 100 -y 30 -k Enter -w Playing`、
`tests/drive.sh -x 62 -y 20 -q 周杰伦 -k Enter -w Playing`（62 列下量得 rail 61 格，不折行）。
`docs/ARCH-tui.md`「进度条就是那条活的 rail」「横幅的尾巴是一个位置」「右贴与 `right_edge`」
与字形库存表已同步。

### 阶段 2：光标强调条与在播行底色 —— **已完成（2026-09-10）**

**1. 光标记号 `▶` → `▎`（`GL_CURSOR`）** —— 已做。三角是个指针，指向标题第一格；
光标选的是**一行**，所以记号是立在整行旁边的一道竖笔。也顺手解决了在播行的 `▶`
与光标的 `▶` 同形互抢。

**2. 槽宽改为量出来的（`mark_w`）** —— 已做，并且比原稿更严。`▎` 进 `CW_AMBIG`
（本节原稿写的 `CW_NARROW` 是错的，见下面那条已改的警示）。槽宽没有手写 `CW_AMBIG_W + 1`，
而是 `disp_w(GL_CURSOR) + 1`：对 `▎` 它恰好等于 `CW_AMBIG_W + 1`，
而对 `YT_ASCII=1` 的 `>` 仍然是 2 —— 手写那个式子会在这里多算一格。
填了的槽与空的槽都由同一个式子生成。已在 `YT_AMBIG_WIDE=1` 与默认两档下截屏比对，
标题列在两档下都不移位。

**3. 底色 —— 落在「在播行」，不是原稿写的「选中行」。** 原稿把 `\033[7m` 认成了选中行的底；
它是**在播行**的底（`C_ROW_HL`），而选中行从来没有底色，靠 `C_MARK` 记号加粗体标题。
按裁决只柔化在播行：`C_ROW_HL` 换成强调色调出的淡底，**`\033[7m` 保留为地板**，
在 `COLORTERM_TC=0` / `--color never` / `NO_COLOR` / 管道下仍然生效 ——
源码原有的那条不变式（关了颜色也要能说出哪行在播）没有被放弃。
选中行仍然没有底色，屏上始终只有一块底。

**4. 底色从强调色调出来，且对着真实背景调。** 原稿写死的 `48;2;26;27;38` 没有采纳：
那是 tokyonight 暗色底，在 latte / one-light / gruvbox-light 上是一块黑疤。
调色板只有强调色、没有底色，所以底色按比例混合（`row_hl_from_accent`，
`ROW_HL_MIX_DARK=30` / `ROW_HL_MIX_LIGHT=18`）。
**第一版按"强调色的百分之几"算，实测两个主题看不见** —— nord 得到 (40,57,62) 压在自己的
`#2e3440` (46,52,64) 上是同一个亮度，gruvbox 暗色同样落在 `#282828` 五个点以内。
改为从背景朝强调色走一小步；背景色取自 `detect_bg` 那次 OSC 11 回复里**本来就有、
从前被丢掉**的 RGB（新的 `BG_R/G/B`）。不多发查询、不多依赖。
终端不肯答时（tmux、`TERM=dumb`、`YT_BG` 写死、`$COLORFGBG`）退回假定的黑/白，
是同一个式子换背景，不是第二条路径。`minimal`/`mono` 没有可混合的 RGB，落回反白地板。

已验证：`bash -n shell/*`；`tests/contract.sh --offline` 273 ok / 0 failed；
`drive.sh` 100x30 默认档与 `YT_AMBIG_WIDE=1` 档各截一帧（槽位对齐）、
`-k 'Down Enter' -w Playing` 一帧（选中与在播同一行，版式无损）；
十个主题 × 明暗的底色在 `/bin/bash` 3.2 下逐一算出并与各自主题底色比对，全部可辨；
`\033[48;2;…m` + `\033[K` + CHA 的 back-colour erase 在 tmux 下单独探测确认覆盖跳格段。
`docs/ARCH-tui.md`「一行的两个状态是正交的」「底色是画法上的一个顺序问题」
「亮色与暗色终端都拿到一个读得清的强调色」与字形库存表、宽度预算表已同步。

### 阶段 3：音源品牌胶囊 —— **已完成（2026-09-10）**

原稿这一节写的是三族徽章（音源品牌、音质/试听权限、VIP）加一个 `render_pill` 函数。
**落地的只有音源品牌那一族**，另两族没做；那个函数一行也没用上。三处出入都是 grounding
推翻了前提之后按实测改的：

**1. `render_pill` 直接嵌 SGR，会当场破坏宽度契约 —— 颜色改走自己的通道。**
`disp_w` 的契约写明"量纯文本，颜色在打印时施加"，而状态段有**两条**路径都要量它：
行内右贴那一整串（量出 `st_w` 再用 CHA 落到 `right_edge`），以及宽度不够时掉回自己一行的
`print_hints`（逐个 item 量 key）。原稿那个函数把 `\033[48;2;…m` 打进段落文本里，
那 ~20 个字节会被算成 ~20 格，右贴就落错列。改为 `PILL_MARK`（`\x1f` + SGR + `\x1f` + 文本）：
`source_seg` 产出这条形状，状态段的拼串循环一次遍历同时产出**打印串**与**测量串**，
`print_hints` 认同一条形状 —— 两条路径共用同一份纯文本，不可能各说一套宽度。
已在 120 列真实帧上量得状态行末格恰好落在 `right_edge`（118），若量的是带转义那一串，
这一行会短二十来格。

**2. 字是 token（` ne `）而不是品牌全名（` NetEase `）。** 已在 88 与 62 列下并排渲染两版
给出判断。那个 token 是 `--engine` 收的词、也是行按自己的 `engine` 字段路由时用的词，
换成全名等于让读者在两套词汇之间做翻译，换来的只有宽度：状态段 39→46 格，
行内右贴门槛（`st_w + 29`）从 68 列推到 75 列，于是一台 72 列终端从此多花一行 chrome、
少一行结果。带底色的 token 是 41 格 / 70 列。落点也只取**状态行第一段**一处：
横幅右贴要在那条按价值丢弃的链上插第四个字段并从标题预算里扣格，而搜索视图下它与状态段同源。

**3. 音质与 VIP 那一族不是渲染改动，数据根本没进 TUI —— 整族退回 `ROADMAP.md`。**
`access`（`full`/`preview`/`paywalled`）只存在于 `ne-search`/`ne-resolve` 的信封里，
`load_rows` 建的是 `R_TITLE/R_DUR/R_VIEWS/R_CHAN/R_LIVE/R_ENGINE/R_RAIL`，**从不读它**；
yt/bili 没有对位字段。更决定性的一条：两个 ne 动词默认就 `select(.access == "full")`，
所以**默认配置下屏上每一行都是 `full`**，`全曲` 会是一枚贴在每行、什么都不说的常量徽章。
而且它是**行级**事实，原稿把它放状态行，对其余行就是假陈述（与"状态行的 `auth=` 不给混源列表"
同一条理由）。它现在是 `ROADMAP.md`「还没定的事」里的一条，两个待决问题写在那里。

**4. 底色的三档，各自只发它所在主题已经许诺过的东西。** 原稿只写了"真彩发 RGB、否则 `\033[7m`
反白"。反白没有采纳（那是 `C_ROW_HL` 刚从阶段 2 退下去的地板，在在播行的淡底上会打架），
改为：`mono` 不发底色，`minimal` 发 ANSI-16 索引且**在真彩终端上也走这一档**
（minimal 的性质是"红是什么由用户终端说"，一个索引正好是这句话，RGB 不是），
其余主题真彩发品牌 RGB、否则退回同一个索引。品牌底色是**身份不是状态**，
这是"一个强调色"那条正本记录在案的例外，理由与边界写在 `ARCH-tui.md`。

已验证：`bash -n shell/*`；`tests/contract.sh --offline` 273 ok / 0 failed（31s）；
`drive.sh` 真实帧 —— 120x30（行内右贴档，末格落在 118；胶囊后 dim 正确重新武装）、
100x30（`print_hints` 回退档）、62x20 + `周杰伦` + 中文 chrome（窄终端不折行）、
`YT_THEME=mono`（裸 token，无底色）、`YT_THEME=minimal`（`41;97`，无 RGB）、
`NO_COLOR=1`（整行无转义）；以及 3.2 下按 主题 × 真彩 × 五个引擎 token
（含 `ne+yt` 混源与未知 `sc`）逐档算出胶囊串比对。
`docs/ARCH-tui.md`「音源胶囊是屏上唯一一处颜色不属于主题的地方」「段落是纯文本加一条颜色通道」
与 minimal 档的转义集合那一句已同步；退回去的那一族写进了 `ROADMAP.md`「还没定的事」。

### 阶段 4：底部快捷键导航栏“键帽化”（Keycap Cheatsheet）

修改 `shell/uting:3700-3850` 的 `print_hints`：
- 放弃长串圆点连接散文，重构为整齐划一的紧凑键帽排版：
  ```text
  [Enter] 播放   [Space] 暂停   [b] 歌单   [h] 历史   [c] 分P   [/] 过滤   [t] 主题   [q] 退出
  ```
- 键位名（如 `[Enter]`）使用加粗高亮（`${C_BOLD}${C_CYAN}`），动作说明使用 `C_DIM` 灰度，消除散乱视觉噪点。
