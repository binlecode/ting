## 横切规范 —— 每个新功能都要过的判据

这几条不描述代码，它们是**提案的过关条件**：一条新功能、一个新键、一条新提示进来之前，
先拿它们量一遍。写在这里而不是 `ARCHITECTURE.md`，因为那一份装的是**已落地的决定**，
而这些是**约束未来**的东西 —— 与下面那些 NO 同一性质，只是形状是"必须"而不是"不做"。

- **一个功能必带 agent 面。** 人有按键，agent 就要有动词加一个 `-j` 信封。
  **理由**：这套东西的定位是 agent 优先（`ARCHITECTURE.md`「定位与设计目标」），
  一个只有键位的功能只做了一半。**它挡住的形状**：先给 TUI 加个键、"agent 面回头再说"。

- **按下前可预期 —— 分清"根本做不了"与"答案可能是没有"。**
  **一、结构上做不了的键，不许占一格**：如单引擎下的 `e`、未装存储时的 `a`/`b`/`d`，
  按前即可判定，必须在界面上门控排除。
  **二、`c`/`i` 是提问键**：问的是行内是否还有分 P 或详情，"没有"是合法答案。
  提问键由三条硬约束管理：提示进帧不偷下一个按键、否定答案带回基础元数据、单槽缓存不买第二次。
  **严禁**由 UI 启发式猜测信号（`ARCHITECTURE.md`「站点知识的边界」）。

- **只为一个答案停下来。** 界面阻塞等键，只能是因为它真的要一个**答案**（歌单名、`y/N`）。
  一条不需要回答的消息是**帧的内容**，由那唯一的渲染器画出来，下一次状态变化就没了。
  **判据**：要么进帧，要么别占屏（`ARCHITECTURE.md`「人机面」）。

- **付了的代价不丢。** 用户明确触发的网络往返，取回的数据必须落屏；不因"没有行可换"
  就把整份丢弃。

## 记录在案的 NO

每条一个形状：**决定 · 理由 · 重开条件**。已否决的方向不保留死线索与废弃执行细节，只留结论。

- **打包 NO —— 公开，但不为分发打包。**
  **决定**：不打包、无 installer、无包管理器 formula、无发布 tag，以参考实现形式公开。
  **理由**：支持面维护成本大于差异化收益（`ARCHITECTURE.md`「六条发现」第 1 条）。
  **重开**：确需单文件二进制分发（由 Go 重写 NO 承接）。

- **喜马拉雅 NO —— 不做喜马拉雅音源引擎。**
  **决定**：不收录喜马拉雅音源。
  **理由**：端点依赖动态令牌鉴权且缺少公开搜索接口；仅有解析没有搜索违反引擎契约（`ARCHITECTURE.md`「平级动词，没有内核」）。
  **重开**：出现免动态鉴权的公开搜索与解析接口。

- **ut-search NO —— 不做跨引擎聚合搜索动词。**
  **决定**：不做跨引擎合并搜索命令 `ut-search`。
  **理由**：聚合动词仅提供 fan-out 与信封合并，砍掉即消除冗余拼法（`ARCHITECTURE.md`「平级动词，没有内核」）；且各引擎数据形状互异，统一信封成本过高。调用方可直接在外部循环调用各引擎。
  **重开**：调用方明确要求输出跨引擎合并的单一信封。

- **list= NO —— 一条 URL 里的 `list=` 不变成一个队列。**
  **决定**：忽略 URL 中的播放列表参数，仅提取当前单曲。
  **理由**：URL 参数解析仅处理单曲标量（如起播偏移）；展开整张清单涉及分页抓取与队列所有权，超出单曲解析范围。
  **重开**：确立列表导入的数据契约与所有权模型（归属 `<engine>-resolve`、`ut-playlist` 还是独立动词）。

- **`--vo-tct-algo=plain` NO —— viz 不提供"满格"这一档。**
  **决定**：音频可视化（viz）拒绝 `plain` 降采样算法，仅提供 `half-blocks`。
  **理由**：`plain` 降采样产生杂色与边缘模糊，牺牲显示质量；节省的字符带宽并非瓶颈。
  **重开**：终端吞吐存在极端瓶颈且画布同步下调至 `rows × 1`。

- **图片不走 mpv 的 VO NO —— 终端里画图这件事，mpv 不是那个后端。**
  **决定**：终端图片显示（封面等）严禁使用 mpv 的视频输出驱动（VO）。（封面已由 TUI 进程发射 Kitty 协议落地，mpv 仅以 `--vo=image` 充当后台转码器，详见 `ARCH-tui.md`「封面」）。
  **理由**：mpv VO 语义为独占全屏终端而非局部嵌入组件（附带清屏与夺取输入控制）；全量未压缩重传带宽开销过大；且拒绝引入外部图形库依赖（详见 `ARCH-tui.md`「封面」）。
  **重开**：mpv 原生支持不接管终端屏幕与输入的局部嵌入模式。

- **Go 重写 NO —— 不做 Go 版。**
  **决定**：拒绝将套件以 Go 等编译型语言重写。
  **理由**：核心价值在 CLI 契约与生命周期安全边界，与实现语言无关；引擎依赖外部站点，shell 原地可改性不可替代；重写无法消除外部运行时依赖，且带来状态机与生命周期的大规模回归风险（`ARCHITECTURE.md`「六条发现」）。
  **重开**：确需独立交付官方 MCP Server 门面，或打包 NO 反转。

- **按键注册表 NO —— 键位不进一张表。**
  **决定**：按键处理保持原生分支匹配，不抽象为全局按键映射表。
  **理由**：键位有效性由上下文表达式动态门控，表驱动增加维护间接层，且本套件无自定义键位需求。
  **重开**：确需支持用户自定义键位映射。

- **terminfo 探测 truecolor NO —— 不查 terminfo 的能力位。**
  **决定**：真彩色探针仅检查 `COLORTERM`，不查询 terminfo 的 `RGB`/`Tc` 位。
  **理由**：主流复用器与现代终端均透传 `COLORTERM`；宿主自带旧版 ncurses 对能力位探测存在假阴性。
  **重开**：宿主环境更新至原生支持真彩能力位，或出现支持真彩却不设 `COLORTERM` 的主流终端。

## 还没做的事（按 ROI 排序，每条等着自己的前置）

- **【高 ROI】容器对象的抽取与导入动词（原「容器行」）** —— 一条搜索结果 ≠ 一个可播对象。
  **收益**：极高。打通专辑、合集与歌单展开链路，大幅提升人与 Agent 批量召回与入队能力。
  **成本**：中等。行模型已锁定（容器不是行，`kind` 收窄至 {`track`, `multipart`}，`ARCH-cli-contract.md`），无破坏性契约风险；需设计专属抽取动词与入队流。
  **待决问题**：容器（频道、专辑、歌单、收藏夹）如何展开为条目清单。
  **前置问题**：裁定所有权归属：作为 `<engine>-search` 扩展动词、`<engine>-resolve` 扩展动词（类比 `--parts`），还是 `ut-playlist` 导入信道。与 `list=` NO 属同源问题，统一裁决。

- **【中高 ROI】B 站音频区（`au` 号）歌词管线打通。**
  **收益**：中。补齐 B 站音源的字幕/歌词能力，与 YouTube / 网易云实现 `--transcript` 能力对齐。
  **成本**：低。yt-dlp 底层 `BilibiliAudioIE` 已暴露 `song.lyric`；信封管线已存在；仅需接通解析入口。
  **待决问题**：将 yt-dlp 暴露的音频区歌词对接到 `bili-resolve --transcript`。
  **前置问题**：界定音频区与视频区搜索结果的命令与参数边界（音频区 URL / 纯 `au` 数字识别）。

## 还没定的事（按 ROI 排序，设计方向的待裁决项）

前置不是代码，是一个决定 —— 所以与上面那节分开放。

- **【极高 ROI】第三方引擎边界 —— 进仓统一维护 vs 外部独立建仓。**
  **收益**：高。直接决定代码库维护半径，防止外部站点频繁变动或反爬风控拖累主套件稳定性。
  **成本**：极低。纯架构与生态决策，无需编写代码。已有「加一个引擎」清单作为独立对齐规范。
  **待决问题**：第三方音源引擎对进本仓统一维护，还是各自成仓仅依靠 CLI 契约对齐（`ARCH-cli-contract.md`）。

- **【中 ROI】viz 的配色要不要可配。**
  **收益**：中。满足个性化终端美化诉求，不影响播放核心功能。
  **成本**：低。仅需在 `config` 增加单个颜色键并由 `ut-play` 透传至 mpv 参数。
  **待决问题**：是否引入独立配色配置项（如 `UT_VIZ_COLOR` 与 `--viz-color`）覆盖硬编码 cyan。
  **已决约束**：严禁复用 `uting` 的 `YT_THEME`（调色板不跨进程共享）。

- **【低 ROI】MCP 官方包装层（stdio server）。**
  **收益**：中低。最新实测（`RESEARCH-tui-player.md` §10）证实外部 MCP 工具均无法托管播放生命周期；而本仓裸 CLI 契约天然可被 Coding Agent（Claude Code / Codex）无损驱动。
  **成本**：高。需引入长连接 JSON-RPC 通信与额外运行时封装，是开启 Go 重写 NO 的唯一业务前置。
  **待决问题**：是否需要官方封装一层 MCP stdio server，还是保持由 Agent 直接调用通用 CLI 动词？

- **【低 ROI / 架构冲突】下载器归属与形态 —— 是内置动词还是保持非目标。**
  **收益**：低。核心使用场景为背景流媒体在线播放，外部调用方已可直接调用底层 `yt-dlp` 独立下载。
  **成本**：高。离线文件管理、断点续传、进度回调会大幅膨胀工具链，且易将轻量引擎误导为“完整下载客户端”。
  **待决问题**：是否提供离线音视频流转存动词？还是坚持“解流与播放分离、不做完整客户端”的定位（`ARCHITECTURE.md`「站点知识的边界」），将离线转存彻底留给外部调用方自行处理？
